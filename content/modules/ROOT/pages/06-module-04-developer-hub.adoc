== Part 1 — Developer Hub and Developer Lightspeed

=== Know

_Red Hat Developer Hub (RHDH) is the Internal Developer Platform (IDP) for Parasol -- a single pane of glass where developers can discover applications, APIs, and documentation, provision environments through self-service templates, and get AI-assisted guidance. It accelerates onboarding by giving new developers everything they need in one place: a software catalog, golden path templates, integrated CI/CD visibility, and now AI-powered assistance through Developer Lightspeed._

**Business challenge:**

* Developers spend excessive time discovering services, APIs, and documentation across fragmented tools
* No single source of truth for what components exist, who owns them, and how they relate
* New developer onboarding takes weeks of knowledge transfer and tribal knowledge sharing
* Developers lack context about the projects they work on and need to interrupt teammates for answers
* Onboarding a new developer to the application landscape takes weeks

**Value proposition:**

Developer Hub provides a centralized, searchable catalog of all applications, components, APIs, and documentation. Developer Lightspeed integrates AI directly into the IDP (not the IDE -- that is the job of coding assistants and extensions such as Roo Code with Model Context Protocol, which we saw in Section 1). Lightspeed combines product documentation, developer documentation, and the software catalog to answer developer questions in natural language, speeding up development and reducing onboarding friction. The platform engineer configures Lightspeed to use the IT-approved model, so developers get AI assistance within governance guardrails.

== Part 4 — Maintaining the golden path (platform engineer persona)

=== Know

_Part 3 showed a developer consuming a golden path: one field, a feature branch, a provisioned environment. That is day one. Day two is harder. A golden path that nobody updates becomes tomorrow's legacy stack. When Quarkus ships a security fix, Parasol cannot open a ticket against every team that scaffolded a service last quarter. The platform engineer updates the Software Template once. Developer Hub finds every application created from that template and opens a reviewable merge request._

**Business challenge:**

* Golden-path templates drift from the applications created from them the moment a developer pushes the first commit
* A CVE in a shared runtime (Quarkus, a base image, a pipeline task) becomes a portfolio-wide scramble: chat messages, tickets, and inconsistent upgrades
* Silently overwriting application repositories would destroy legitimate project customizations and break trust in the platform
* Platform engineers have no inventory of "which apps came from which template" outside spreadsheets and tribal knowledge

**Current state at Parasol:**

* The **Quarkus Application** template is the blessed starting point for new Java services: source repo, GitOps repo, pipeline, and catalog registration in one Create flow
* Developers already customize those repos. The platform must propose updates, not overwrite them.
* Until Developer Hub tracks `scaffoldedFrom` relationships, the platform team cannot answer "who is still on the vulnerable Quarkus BOM?" without a hunt

**Value proposition:**

Software Templates in Developer Hub are versioned, Git-managed artifacts. Each scaffolded application records the template it came from. When the platform engineer bumps `backstage.io/template-version` and changes the skeleton (for example `quarkus.platform.version` in `pom.xml`), the `scaffolder-relation-processor` plugin diffs the new skeleton against every downstream source repository and opens a GitLab merge request. The developer reviews and merges. The golden path stays golden without a ticket storm, and without the platform team force-pushing into product code.

Q: "How does Developer Hub know which repositories to update?"::
A: "Each scaffolded `catalog-info.yaml` sets `scaffoldedFrom: template:default/quarkus-app`. The relation-processor plugin walks those catalog relationships, resolves each entity's source repository, diffs the current skeleton against the repo, and opens the merge request. No extra inventory."

Q: "Can this overwrite a team's customizations?"::
A: "The default plugin compares the *current* skeleton to the *current* repo. If a team has edited files that also live in the skeleton — `pom.xml` is the usual example — those edits show up in the merge request next to the real template change. Always review before merging. Unresolved scaffolder placeholders and stripped Jinja conditionals can also appear. That is why this is a merge request, not an auto-merge."

Q: "The merge request is noisy. Can we send only the lines that changed in the template?"::
A: "Yes — that is the scoped-diff alternative, closer to how tools like `copier` or `cruft` update projects. The bundled plugin has no 'diff only what changed between two template versions' mode yet; it always diffs the live skeleton against the live repo. For a demo, two scripts in this showroom (`content/modules/ROOT/examples/template-lifecycle/`) stand in: `disable-automated-lifecycle.sh` turns off the plugin's own merge requests (and adds Argo CD `ignoreDifferences` so GitOps does not flip the flag back), then `propagate-skeleton-diff.sh` diffs the last two GitLab commits scoped to `templates/quarkus-app/skeleton` and opens a merge request only where that patch applies cleanly."
+
[source,bash,role="copypaste"]
----
./disable-automated-lifecycle.sh              # apply; --dry-run to preview
./propagate-skeleton-diff.sh                  # open scoped MRs; --dry-run to preview
----
+
Copy the scripts from the showroom repo to a machine with `oc` logged into the demo cluster (`git` and `python3` required). This demo uses OIDC, so the propagate script reads `RHDH_TOKEN` from `backend-secret` / `BACKEND_SECRET` unless you export one. The scripts are a demo stand-in, not a production control plane: the same detection, catalog lookup, and merge-request flow already live in the plugin. A production fix is a scoped `diffMode` (or equivalent) on `scaffolder-relation-processor`, not a shell wrapper around `oc`.
+
image::rhdh-lifecycle-scoped-diff-mr.png[GitLab merge request containing only the pom.xml Quarkus version bump, without unrelated skeleton files,link=self,window=blank,align="center",width=700,title="Scoped diff: only the template change, not a full-repo compare"]
